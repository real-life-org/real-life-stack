Module und Toolkit wissen nicht, wie sich jemand anmeldet. Sie fragen den Connector, ob er Anmeldung kann, welche Wege er anbietet und wer gerade angemeldet ist. Ob dahinter ein Schlüsselpaar im Browser steht oder ein Konto auf einem Server, entscheidet allein der Connector.

## Der Vertrag

```ts
interface Authenticatable {
  getCurrentUser(): Promise<User | null>
  observeCurrentUser(): Observable<User | null>
  getUser(id: string): Promise<User | null>
  getAuthState(): Observable<AuthState>   // loading | unauthenticated | authenticated + user
  getAuthMethods(): AuthMethod[]          // { method: string, label: string }
  authenticate(method: string, credentials: unknown): Promise<User>
  logout(): Promise<void>
}
```

- **Die Fähigkeit ist optional.** `isAuthenticatable(connector)` prüft sie. Ein Connector, der nur liest, lässt sie weg.
- **Methoden sind Namen, Zugangsdaten sind `unknown`.** Jeder Connector bringt seine Wege mit und legt selbst fest, was er dafür braucht. Ein neuer Weg ändert den Vertrag nicht.
- **`User.id` ist undurchsichtig.** Im Web of Trust ist sie eine DID, bei Supabase eine UUID. Module vergleichen sie, sie lesen nichts aus ihr.
- **Der Anmeldestatus ist ein Observable.** Läuft eine Sitzung ab oder meldet sich jemand in einem anderen Tab ab, schließt sich die App wieder.

## Die Connectoren

| Connector | Wege (`authenticate`) | Identität | Wer bürgt für den Autor |
|---|---|---|---|
| `wot` | `generate`, `create`, `mnemonic`, `unlock` | `did:key` aus zwölf Wörtern, Schlüssel im Gerät | die Signatur, jeder kann sie prüfen |
| `supabase` | `email`, `email-signup`, `anonymous` | Supabase-UUID, Sitzung über supabase-js | der Server, über Row-Level-Security |
| `local` | `local` | ein lokaler Nutzer je Browser oder Tab | niemand, nur zum Ausprobieren |
| `mock` | `mock` | der erste Beispielnutzer | niemand, nur für Demos |

Der WoT-Connector nennt in `getAuthMethods()` nur `did` als Anzeigenamen. Sein `authenticate` kennt `did` nicht, sondern die vier Schritte aus der Tabelle. Die Liste beschreibt dort also nicht die aufrufbaren Wege.

In beiden echten Connectoren kommt der Autor eines Eintrags aus der Sitzung, nie aus den gesendeten Daten. Wie die App das in Knöpfe übersetzt, steht unter [Fähigkeit, Berechtigung, Herkunft](/handbuch/rechte/).

## Wer den Anmeldebildschirm zeigt

Die Referenz-App entscheidet in ihrem `AuthGate`:

- **Web of Trust:** Der WoT-Connector bringt mit `DIDAuthScreen` einen eigenen Ablauf mit. Er erzeugt die Wörter, lässt sie sichern, setzt eine Passphrase und kann eine Identität wiederherstellen oder entsperren.
- **Alle anderen:** Der `AuthScreen` aus dem Toolkit liest `getAuthMethods()` und zeigt die Wege, die er kennt: `email`, `email-signup` und `anonymous`.

Ein Connector mit einem anderen Weg, etwa einer Anmeldung per DID-Signatur, findet heute im `AuthScreen` keinen Knopf dafür. Der Vertrag trägt den Weg, die Oberfläche noch nicht.

## Eine App, eine Identität

Eine App hält genau einen Connector. Wer sich anmeldet, ist damit für die ganze App diese eine Identität. Spaces aus verschiedenen Quellen in einer App, und dieselbe Person in beiden, gibt es noch nicht. `MultiSource` steht als Schnittstelle im Paket `data-interface`, aber keine App und kein Modul ruft sie auf.

## Was eine Anmeldung per DID bei Supabase berührt

Eine Person mit WoT-Identität ist bei Supabase heute eine zweite, fremde Person. Wer das ändert, trifft auf diese Stellen:

- **Spalten:** Autor, Mitglied, Einladende und Kontaktpartner sind `text`-Spalten (`created_by`, `user_id`, `invited_by`, `requester`, `addressee`). Sie nehmen eine DID ohne Umbau auf.
- **`auth.uid()`:** Alle Policies vergleichen mit `auth.uid()::text`. Die Funktion liest den `sub` des JWT und wandelt ihn in eine UUID um. Mit einer DID als `sub` schlägt diese Umwandlung fehl.
- **`profiles.id`:** Die Profiltabelle ist über eine UUID an `auth.users` gebunden.
- **Prüfung der Tokens:** PostgREST und Realtime nehmen jedes JWT an, das mit dem `JWT_SECRET` der Instanz signiert ist. GoTrue muss ein Token nicht ausgestellt haben.
- **Signieren:** Der WoT-Connector kann beliebige Daten mit dem Schlüssel der DID signieren (`sign`, `signJws`).
- **Oberfläche:** Der `AuthScreen` braucht einen Weg für die neue Methode, siehe oben.

Wie und in welcher Reihenfolge das gebaut werden soll, beschreibt [Issue #535](https://github.com/real-life-org/real-life-stack/issues/535) (Etappe 4 für die Anmeldung, Etappe 5 für Spaces aus mehreren Quellen in einer App).
