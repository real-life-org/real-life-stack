Modules and the toolkit do not know how anyone signs in. They ask the connector whether it can sign people in, which ways it offers and who is signed in right now. Whether a key pair in the browser or an account on a server stands behind that is up to the connector alone.

## The contract

```ts
interface Authenticatable {
  getCurrentUser(): Promise<User | null>
  observeCurrentUser(): Observable<User | null>
  getUser(id: string): Promise<User | null>
  getAuthState(): Observable<AuthState>   // loading | unauthenticated | authenticated + user
  getAuthMethods(): AuthMethod[]          // { method: string, label: string }
  authenticate(method: string, credentials: unknown): Promise<User>
  logout(): Promise<void>
}
```

- **The capability is optional.** `isAuthenticatable(connector)` checks for it. A read-only connector leaves it out.
- **Methods are names, credentials are `unknown`.** Every connector brings its own ways and decides what it needs for them. A new way does not change the contract.
- **`User.id` is opaque.** In the Web of Trust it is a DID, with Supabase a UUID. Modules compare it; they read nothing out of it.
- **The sign-in state is an observable.** If a session expires or someone signs out in another tab, the app closes again.

## The connectors

| Connector | Ways (`authenticate`) | Identity | Who vouches for the author |
|---|---|---|---|
| `wot` | `generate`, `create`, `mnemonic`, `unlock` | `did:key` from twelve words, key on the device | the signature, anyone can check it |
| `supabase` | `email`, `email-signup`, `anonymous` | Supabase UUID, session via supabase-js | the server, through row-level security |
| `local` | `local` | one local user per browser or tab | nobody, for trying things out only |
| `mock` | `mock` | the first sample user | nobody, for demos only |

The WoT connector lists only `did` as a display name in `getAuthMethods()`. Its `authenticate` does not know `did`, but the four steps from the table. So there the list does not describe the ways you can call.

In both real connectors the author of an entry comes from the session, never from the data sent. How the app turns that into buttons is described under [Capability, permission, origin](/en/handbuch/rechte/).

## Who shows the sign-in screen

The reference app decides in its `AuthGate`:

- **Web of Trust:** The WoT connector brings its own flow, `DIDAuthScreen`. It generates the words, has them backed up, sets a passphrase and can restore or unlock an identity.
- **All others:** The toolkit's `AuthScreen` reads `getAuthMethods()` and shows the ways it knows: `email`, `email-signup` and `anonymous`.

A connector with another way, such as signing in with a DID signature, finds no button for it in the `AuthScreen` today. The contract carries the way; the interface does not yet.

## One app, one identity

An app holds exactly one connector. Whoever signs in is that one identity for the whole app. Spaces from different sources in one app, with the same person in both, do not exist yet. `MultiSource` is an interface in the `data-interface` package, but no app and no module calls it.

## What sign-in with a DID on Supabase touches

A person with a WoT identity is a second, unrelated person on Supabase today. Whoever changes that meets these places:

- **Columns:** author, member, inviter and contact partners are `text` columns (`created_by`, `user_id`, `invited_by`, `requester`, `addressee`). They take a DID without rework.
- **`auth.uid()`:** All policies compare against `auth.uid()::text`. The function reads the JWT's `sub` and casts it to a UUID. With a DID as `sub`, that cast fails.
- **`profiles.id`:** The profile table is bound to `auth.users` by a UUID.
- **Token checks:** PostgREST and Realtime accept any JWT signed with the instance's `JWT_SECRET`. GoTrue does not have to have issued it.
- **Signing:** The WoT connector can sign arbitrary data with the DID's key (`sign`, `signJws`).
- **Interface:** The `AuthScreen` needs a way for the new method, see above.

How and in which order this is to be built is described in [issue #535](https://github.com/real-life-org/real-life-stack/issues/535) (stage 4 for sign-in, stage 5 for spaces from several sources in one app).
